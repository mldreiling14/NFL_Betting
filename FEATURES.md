# NFL Win Probability Model — Feature Reference

This document describes every variable in the `games_with_features` table, produced by running:

```bash
python src/fetch_data.py
python src/build_features.py
```

Source data comes from [`nflreadpy`](https://github.com/nflverse/nflreadpy), covering the 2015–2025 seasons (3028 games, 116 columns as of this revision). Live predictions for upcoming games are generated by `src/predict.py`, served via the Streamlit app (`app.py`).

---

## Plain-Language Glossary

- **EPA (Expected Points Added)**: a single number capturing how much a play (or a player's average play) helped or hurt a team's scoring chances, compared to what's typically expected in that situation.
- **Elo rating**: a "power ranking" number for each team, borrowed from chess. Every team starts at 1500. Beating a strong team raises your rating more than beating a weak one.
- **Rolling average**: how a team/player has done *lately* (e.g. last 5 games), not full-season or career numbers.
- **Snap share**: what % of a team's plays a player was on the field for.
- **Percentile**: where a player ranks against everyone else at their position, league-wide.
- **Correlation**: a number from -1 to +1 measuring how strongly two things move together. The biggest single correlation in this whole project is about 0.19 — a reminder of how much genuine unpredictability the NFL has.
- **Leakage-free**: a feature describing "how a team/player has been doing" only ever uses games *before* the one being predicted.
- **Depth chart**: a team's own official, ranked list of who plays each position — more reliable than "whoever played most recently" for identifying the real current starter.
- **Calibration**: whether a model's stated probability matches reality — e.g., among all games predicted "70% chance," does the favored team actually win about 70% of the time?

**Production model** (`train_model.py`) is a plain logistic regression on 58 features, trained on all 3028 available games. Within ~0.5–1 point of Vegas on the most recent test window.

### Tested and confirmed NOT to help (this revision)

A full round of "how do we push accuracy further" was run and is worth documenting so it isn't re-attempted blindly later:

- **L1-regularized logistic regression (automatic feature selection)**: cross-validation chose almost no regularization penalty (`C ≈ 167`, i.e. barely any), and zero of the 58 features were shrunk to zero. Accuracy was statistically identical to plain logistic regression (67.9% vs 67.7%). **Takeaway: the existing feature set isn't carrying obvious dead weight a linear penalty can detect.**
- **Random Forest / XGBoost**, re-tested on the full mature 58-feature set (not just the original smaller set from early in the project): all three algorithms landed within ~1 point of each other under proper `TimeSeriesSplit` cross-validation (62.0–62.9%). **Takeaway: algorithm choice is not the lever that improves this model further — stick with logistic regression for its simplicity and interpretability.**
- **Isotonic calibration** (`CalibratedClassifierCV`): overall accuracy unchanged (67.2% vs 67.7%). It did **not** fix a specific, real miscalibration found in the 40–50% predicted-probability range (model says ~45–46%, actual home win rate is only ~32%, over 100+ test games — a real, well-supported gap, not noise). **Takeaway: this looks like a genuine blind spot in exactly the hardest-to-call games (near coin-flip predictions), not a general calibration problem a standard correction can fix. Documented here as a known, currently-unresolved limitation — worth revisiting once more seasons of data are available.**
- **Red zone TD rate** (built from play-by-play, per-drive trip-based): real signal confirmed (57.9% vs 53.0% home win rate, above/below median), but redundant with Elo/point differential — accuracy -0.2pts.
- **Two-minute-drill comeback rate** (rate of winning after trailing late in the 4th quarter/OT): real signal confirmed after a bug fix (56.9% vs 52.9%), but redundant with Elo/point differential — accuracy -0.7pts.

## ⚠️ General Rule: "Conditional" Features Require Gap-Aware Projection

**This is the single most important lesson from this project's feature-engineering process, discovered independently twice (star WR injury, then two-minute-drill comeback), and worth applying proactively to any future feature idea shaped like this.**

Some features only naturally have a value in a specific **triggering situation** — a player is injured, a team is trailing late in the 4th quarter, etc. If such a feature is merged directly by `game_id`, the mere *presence* of a value (rather than `NaN`) leaks information about that game's outcome, independent of what the feature is actually trying to measure:

- **Two-minute-drill bug**: merging "this team's rolling comeback rate" only onto games where a trailing situation *actually occurred that game* meant that simply having a non-null value implied "this team was already losing late in this exact game" — teams trailing late lose ~89% of the time, so the feature looked like it strongly predicted losing, when it was actually just a proxy for "the game was already going badly." A real bug, not a real finding — caught by comparing subset win rates against the ~54.8% known baseline and noticing they were absurdly low (~11%).
- **Star WR bug** (documented in the feature section below): an injured player generates no stat row for games he misses, so an early version of "is the primary WR a star" became structurally blind to genuinely injured stars at exactly the moment they were out.

**The fix, both times:** use `pd.merge_asof(..., direction='backward')` to project each team's/player's last known value forward across **every** game they're part of — not just the games where the triggering situation happened — so the feature reflects "this team's standing trait as of today," not "did the trigger event happen in this specific game."

**Before building any future feature that's naturally sparse/conditional (injuries, rare game situations, milestone-based stats), check: would a row only exist when something specific just happened? If yes, apply this projection technique from the start, rather than discovering the leakage as a confusing, counterintuitive result later.**

## Core / Identifier Columns

| Column | Description |
|---|---|
| `game_id` | Unique ID (format: `season_week_awayteam_hometeam`) |
| `season` / `week` / `gameday` | Season, week, date |
| `home_team` / `away_team` | Original/historical team codes |
| `home_team_std` / `away_team_std` | Standardized codes for relocated franchises — used for `load_team_stats`-sourced data only (see warning) |
| `home_score` / `away_score` | Final score |
| `home_win` | **Target variable** |
| `home_coach` / `away_coach` | Head coaches |
| `home_rest` / `away_rest` | Days of rest |
| `div_game` | `1` if divisional matchup |
| `spread_line`, `*_moneyline`, `total_line` | Vegas market lines — benchmark only |
| `roof`, `surface`, `temp`, `wind` | Raw weather |

### ⚠️ Team-code convention warning

- **`load_team_stats`, `load_player_stats`, `load_snap_counts`**: backfill to the **current** franchise code always. Merge on `home_team_std`/`away_team_std`.
- **`load_pfr_advstats`**: uses the **actual code at the time**. Merge on raw `home_team`/`away_team`.

## Engineered Features (Currently in the Model)

### Team Recent Form, QB, RB, WR/TE, Injuries, Defense, Coaching, Elo, Rest, O-Line, DB/WR Matchup, Star Injuries

See prior revisions of this document for full detail on each — unchanged this revision except as noted in "Tested and confirmed NOT to help" above. Summary:

- **Team form/point differential**, **QB EPA**, **Elo** — strongest, most reliable signals
- **RB/WR-TE team aggregates**, **defense-allowed**, **O-line (sack/pressure rate)**, **DB/WR matchup** — moderate, confirmed contributors
- **Star RB/WR injury flags** — small but real signal, kept despite modest accuracy cost, after fixing the gap-aware projection bug described above
- **Coach head-to-head**, **rest advantage** — small, real contributions

### Weather & Climate Shock — built, excluded from production model
Real signal (`cold_shock_game`: 61.6% vs 54.8% home win rate, n=219) but too rare to move overall accuracy. Not in the model; planned as a UI badge instead.

### Red Zone Efficiency & Two-Minute-Drill Comeback Rate — built, NOT in production model
Both real, verified signals (see Model Performance Summary above), both redundant with Elo/point differential once combined in the full model. Code preserved in case future feature-set changes shift this calculus, but currently excluded from `train_model.py`'s `FEATURE_COLS`.

## Live Prediction Pipeline (`src/predict.py`)

### ⚠️ Bug history: "most recently played" vs. "actual current starter"

Fixed for **QB**, **WR**, and **CB** using `nfl.load_depth_charts()` (official ranked depth charts) instead of "whoever played in the team's most recent game" — the latter breaks badly when a real starter is hurt late in a season and backups finish games out (real example: KC's Mahomes injury caused a naive lookup to identify an emergency third-string QB as "current," moving KC's Week 1 2026 prediction from 27.9% to a corrected 46.0% once fixed).

- **CB** has no single "CB1" in depth charts (split into `LCB`/`RCB`) — both starters' own coverage stats are pulled and whichever has better recent completion % allowed is used.
- **RB** team-aggregate stats do **not** need this fix (confirmed: a late-season personnel shift only mildly diluted the aggregate, unlike QB's near-total distortion). A separate `current_rb_starter` (depth-chart RB1) exists as groundwork for future live star-injury detection.

**Current limitation:** star-injury features default to healthy (`0`) in all live predictions, since real injury designations aren't published until close to game day.

## Known Data Quality Notes

- **Relocated franchises**: see team-code convention warning.
- **Missing values**: filled with column means (`SimpleImputer`), except `home_coach_h2h_wins` (neutral `0.5`).
- **"Primary player" selection ties**: filter to the correct position/group with `inner` merge before selecting.
- **Live snapshot aggregation order matters**: team-level features must aggregate to one row per team-game *before* rolling.
- **Conditional/triggered features need gap-aware projection** — see the dedicated section above. This is the single most important, twice-independently-discovered lesson from this project.
- **Vegas comparison caveat**: implied probabilities from moneylines aren't de-vigged/normalized.
